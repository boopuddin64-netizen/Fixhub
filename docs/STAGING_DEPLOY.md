# Fixhub staging deploy (free, no credit card, no paid services)

Host: **Render free web service** (Blueprint: `render.yaml`) + **Supabase free** Postgres (project `fixhub`, London).
Paystack runs in **TEST mode**, SMS/OTP codes go to the **server log**. Nothing here costs money. At launch see "Going live" below.

## Limits of the free host (Render Hobby, verified 2026)
- 512 MB RAM, 0.1 CPU, **750 free instance hours/month** per workspace (one always-on service = 720 h, so it fits; a second free service would not).
- Spins down after **15 min without inbound HTTP**; the next request cold-starts in **~1 min** (Render shows a loading page). Keep it warm with a
  free pinger (cron-job.org or UptimeRobot, every 5-10 min, `GET https://<app-url>/health`). Pinging keeps you inside the 750 h.
- 5 GB outbound bandwidth/month, 500 build minutes/month. No card on file = service is suspended instead of billed if a limit is exceeded.
- **Ephemeral disk**: files written to `./data/attachments/` (customer repair photos) vanish on every deploy/restart/spin-down. Everything else
  lives in Postgres. For the test phase that is acceptable; before launch move attachments to object storage or a paid persistent disk.
- One instance only (the app enforces a Postgres advisory writer lock). Render starts the new instance before stopping the old one, so
  the blueprint sets `EARLY_LISTEN=true` (port opens immediately, `/health` says `starting`) and `WRITER_LOCK_WAIT_MS=120000`
  (the old instance is stopped ~60 s after traffic switches; it flushes state and releases the lock on SIGTERM).

## One-time setup (about 10 minutes)
1. **Render**: sign up at https://render.com with GitHub (no card). Install/authorise the Render GitHub app for `boopuddin64-netizen/Fixhub`.
2. Render dashboard -> **New -> Blueprint** -> select the `Fixhub` repo, branch `main` -> it reads `render.yaml`.
3. Fill the prompted secrets:
   | Name | Value |
   |---|---|
   | `DATABASE_URL` | the Supabase **session pooler** URL (port **5432**), ending `?sslmode=require&uselibpqcompat=true` |
   | `PAYSTACK_SECRET_KEY` | your Paystack **TEST** secret key `sk_test_...` (Paystack dashboard -> toggle *Test mode* -> Settings -> API Keys & Webhooks). Never the live key during testing. |
   | `ADMIN_BOOTSTRAP_EMAIL` | your admin email |
   | `ADMIN_BOOTSTRAP_PASSWORD` | 12+ chars with upper, lower, digit and symbol (one-time; you change it at first sign-in) |
   (`JWT_SECRET` is generated by Render automatically.)
4. **Apply**. First build takes ~3-5 min. Note the URL Render shows, e.g. `https://fixhub-staging.onrender.com`.
   `APP_URL` is filled automatically from Render's `RENDER_EXTERNAL_URL`; only set `APP_URL` yourself if you attach a custom domain.
5. Open `https://<app-url>/health` -> `{"status":"ok",...,"database":"connected"}`.
6. **First admin**: open `https://<app-url>/admin`, sign in with the bootstrap email/password, choose a new password when asked. Then in Render ->
   service -> Environment **delete `ADMIN_BOOTSTRAP_EMAIL` and `ADMIN_BOOTSTRAP_PASSWORD`** (saving redeploys; that is fine).
7. **Paystack test webhook**: Paystack dashboard (Test mode) -> Settings -> API Keys & Webhooks -> Test Webhook URL = `https://<app-url>/api/payments/webhook`.
   (Callback URL is generated by the app from `APP_URL`; nothing to set in Paystack.)
8. **Keep warm** (optional but recommended): cron-job.org / UptimeRobot HTTP monitor on `https://<app-url>/health` every 5 min.
9. **Reading codes**: with `SMS_DEV_MODE` the OTP / reset / phone-verification / e-mail-verification codes are printed in Render -> service -> **Logs**
   as `[STAGING SMS] To: +234... | Message: Your Fixhub ... code is 123456` and `[DEV EMAIL VERIFY] ...`.

## Google keys (all optional for testing)
* **Google Sign-In** needs `VITE_GOOGLE_CLIENT_ID` (baked into the JS at build time). The server verifies the token audience against `GOOGLE_CLIENT_ID`
  (falls back to the `VITE_` one). If unset, the code falls back to a hard-coded demo client ID that only works on the origins Google allowed
  for it, so on your own URL the Google button shows an origin error while **email/password login keeps working**. No client secret is used anywhere.
  1. https://console.cloud.google.com -> create project `fixhub` (free, no card).
  2. APIs & Services -> OAuth consent screen -> External -> app name, support email -> Save. Leave in *Testing* and add your test Gmail addresses as test users
     (or *Publish app* so anyone can sign in; basic scopes email/profile need no verification).
  3. Credentials -> Create credentials -> OAuth client ID -> **Web application** -> **Authorized JavaScript origins** = `https://<app-url>` (exact origin, no path, no trailing slash;
     add `http://localhost:3000` for local). No redirect URIs needed (Google Identity Services popup/button flow).
  4. Copy the Client ID -> Render env `VITE_GOOGLE_CLIENT_ID` (and optionally `GOOGLE_CLIENT_ID`) -> **Clear build cache & deploy**.
* **Google Maps** (`VITE_GOOGLE_MAPS_API_KEY`, optional `GOOGLE_MAPS_API_KEY` for server reverse-geocoding): **skip for testing.** Without a key the app degrades gracefully: the location
  step uses the built-in Nigerian area catalogue search + GPS, reverse-geocoding falls back to OpenStreetMap Nominatim (free, no key), no map widget/Places autocomplete.
  Maps Platform requires a billing account (card) even though there is a monthly free credit; if you enable it later: enable *Maps JavaScript API*, *Places API (New)*, *Geocoding API*,
  create an API key, restrict it by **HTTP referrers** to `https://<app-url>/*` (browser key) and, for a separate server key, by API (Geocoding only).

## Going live (later)
Remove `ALLOW_PAYSTACK_TEST_KEY`, `SMS_DEV_MODE`, `ALLOW_SMS_LOG_OTP`; set `PAYSTACK_SECRET_KEY` to the **live** key (`sk_live_...`) yourself in the dashboard; set `SMS_PROVIDER_API_KEY`
(Sendchamp, funded account); switch Paystack live webhook to the same URL; upgrade Render to a paid instance (no spin-down) and Supabase to Pro (backups); move attachments off the ephemeral disk.
With a live key the server refuses `SMS_DEV_MODE` at boot, so OTPs can never be logged in production by mistake.
